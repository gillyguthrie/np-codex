# NP Codex — community knowledge base skill

This skill is self-contained: you do NOT need a local copy of the knowledge base. Answers come from the live data files in the public repo, so every user always queries the current version.

**Data root:** `https://raw.githubusercontent.com/gillyguthrie/np-codex/main/`

## How to answer any NP question

1. Pick the data file for the topic (map below).
2. Fetch it from the data root (e.g. `.../main/data/mechanics.json`). Always fetch from the repo — it is the single source of truth, and fetching live means every answer reflects the current version. Do not answer from a local copy of the data unless the user explicitly directs you to one.
3. Read or compute the answer from that JSON — with code, for anything multi-number.
4. If a fetch of the data root is REFUSED (some clients only fetch URLs the user sent or that appeared in search results), recover in this order — never answer from memory at any step: (a) ask the user to reply with this link so you can fetch it: https://raw.githubusercontent.com/gillyguthrie/np-codex/main/ — a link the user sends is fetchable in every client; once they send it, append the data file path you need and fetch. (b) If fetching is unavailable entirely, ask the user to paste the relevant data file's contents, or to read the value themselves at https://github.com/gillyguthrie/np-codex. Do NOT burn turns web-searching for the repo — searches for 'np-codex' return unrelated projects. Tip for users: including the repo link in your first message guarantees lookups work.

## The rules (binding — full text in GOVERNANCE.md at the repo root)

1. **Never state a load-bearing number from memory.** Every magnitude, cost, %, formula constant, or stat must come from the fetched `data/*.json` in the moment, or be computed by code over it. This applies to conversation, not just documents.
2. **NP is not vanilla Morrowind.** If a value "feels known" from vanilla or UESP, that is the signal to look it up — never to answer from training data. (Canonical trap: the Atronach birthsign has Spell Absorption 15 on NP, not vanilla's 50.)
3. **If the KB doesn't know, say so — then point at the community.** A `null` value with a status, or a missing record, means "not in the KB" — report that, check `data/open_questions.json` for a matching known gap, and do NOT fill the hole from any outside knowledge. Instead, direct the user to ask in the **#server-general channel of the Nerevarine Prophecies Discord** — the community is the living source for anything the KB hasn't captured yet. When the KB has only scattered speculative fragments on a topic (records tagged as speculation/provisional), say plainly that the KB has no settled answer, present the fragments clearly labeled as speculation, and point to Discord — don't stitch fragments into something that reads as established.
4. **Check `data/contradictions.json` before calling anything settled — and read its `status`.** A record with `status: "resolved"` is settled: report the adopted value from its `resolution` field as the answer (the competing positions are an optional footnote, not a live dispute). Only an unresolved record is contested: present both positions with dates, never one of them flatly.
5. **Respect confidence tiers**: dev-stated > measured > player-reported > provisional > contested. Provisional values (e.g. the anvil AR multiplier) must be flagged as provisional when used. (Melding Construct is settled: +20% equipment AR at rank 5, measured; the +4%/rank split is an assumed-linear interpolation — flag only the split if a mid-rank value is load-bearing.)
6. **Dates and eras matter — and the current 0.8 server is the ONLY default frame.** Patch-sensitive values (anvil, camps, meta) carry dates/era tags; prefer current-era values and say when a figure is old. **0.7-era content (pre-2022-05-13 — the old server: its systems, Nerevarine Tokens, old racials/birthsigns, old events, retold history) is outdated history: never volunteer it, mix it into a current-server answer, or let it pad a response.** Bring it up ONLY when the user explicitly asks about server history, the 0.7 era, or how something changed — and then label it plainly as 0.7-era history (`lore:07-to-08-transition` is the anchor). Era preference is about data currency, NOT advice: when *recommending* (which camp to farm, what to build), fit the answer to the user's stated level and goals — the newest content is often the hardest, not the best suggestion.
7. **This codex is NP-first — vanilla content splits in two.** Vanilla item **stats** (armor, weapons, clothing/jewelry) ARE covered: `data/vanilla_ref.json` is parsed directly from the game's ESM files — use it for "what are vanilla X's stats" and for NP-vs-vanilla comparisons (NP items link to it via `xref["vanilla-ref"]`; mind the AR convention below). Vanilla **lore IS covered**: `data/vanilla_lore_books.json` (449 in-game books/notes/scrolls, summarized — never reproduce book text) and `data/vanilla_lore.json` (storyline arcs + contested questions; its `contested_is_canon` convention is binding — the great lore contradictions are authored content, answered by presenting the competing traditions flatly, never resolved). Vanilla **quests, NPCs, and anything not in the vanilla files**: say the codex doesn't cover it and refer the user to the **UESP Morrowind wiki** (https://en.uesp.net/wiki/Morrowind:Morrowind). Never assert any vanilla value or vanilla-vs-NP difference from memory — if it's not in vanilla_ref.json or a `vanilla_note` field, it goes to UESP.
8. **Item locations**: for NP/server items, return the record's `location` (and `drop_notes`) field. For vanilla-named items, `data/vanilla_locations.json` has the vanilla baseline (world placements, containers, restocking sellers, leveled lists) — answer from it, labeled as the vanilla baseline. If neither knows, say the KB doesn't record it and refer the user to **#server-general on the NP Discord**.
9. **Every data file's `_meta.conventions` block is binding for that file — read it before computing over that file's records.** This SKILL.md only changes for cross-cutting rules or when a new file enters the map; per-file reading rules live in that file's `_meta`, and file-map entries stay to about two lines.

## Which file answers what (all under `data/`)

Fetch only the file(s) the question needs — the two catalogs are big. For conceptual/formula questions start with `mechanics.json`; don't pull a catalog just for one example.

- `mechanics.json` (~30 KB) — formulas, constants, established facts (HP/Magicka/Fatigue/AR formulas, caps, tick length, proc rates). **Tool authors: import constants from here — never hardcode.**
- `items.json` (~1 MB — fetch only for item lookups) — all server items, weapons included (~700 records). AR values use the skill-100 tooltip convention (see `formula:ar-capture-normalization` in mechanics.json); `captured:false` records are known-to-exist stubs; `origin_game` marks vanilla-named vs server-created items.
- `masteries.json` (~730 KB — fetch only for mastery lookups) — the mastery tree (~890 records). `raw_text` is the authoritative effect wording. **Multi-rank families stack: each rank's stated magnitudes are increments, so owning ranks 1..N sums them all** — with one exception: Shadowstalker's critical-strike-damage % is Mug-style replacement, the highest owned rank's % only (rank 3 = 90%). See `_meta.conventions`.
- `birthsigns.json`, `races.json` — the 0.8 dev rework tables, verbatim; `vanilla_note` fields are context only, never valid NP values.
- `camps_events.json` — camps, bosses, holiday events (each camp carries `status`/era notes — two camps can share a nickname like "the fire camp"; prefer `current-era`, and ask which one if unclear). `enchanting.json` — self-enchant ceilings + Infusion Anvil (era-tagged). `server_rules.json` — rules verbatim. `lore.json` — server lore. `lore_texts.json` — verbatim community-authored in-world texts (e.g. the Horky scriptures) for exact read-back on request; its `_meta.conventions` govern (label as community fiction, attribution withheld until authorized, read `[name withheld]` markers as written). `archetypes.json` — community build archetypes (player-reported, costs as claimed; **check each record's `cost_semantics`**: `cumulative` means claimed_cost is a running total — read the final entry, never sum the array).
- `alchemy.json` — alchemy ingredients: 126 vanilla (ESM-parsed baseline; NP may modify) + NP-custom ingredients as captured. Effects listed in game order (order = reveal order by skill).
- `vanilla_processes.json` — how VANILLA alchemy, enchanting, and armor repair work (ESM constants + engine-documented formulas), kept as the baseline to diff NP's modified processes. For NP enchanting answers use `enchanting.json`, not this.
- `vanilla_lore_books.json` (~440 KB — fetch for lore/book lookups) — all 449 vanilla in-game texts summarized (type, summary, topics, characters, storylines). VANILLA lore only; NP lore stays in lore.json.
- `vanilla_lore.json` — vanilla storyline arcs (15) + the contested questions (Red Mountain, Tribunal divinity, Dwemer fate, ...). Start lore questions here; pull the books file for specifics.
- `vanilla_locations.json` (~2 MB — fetch only for where-do-I-find-it lookups) — vanilla item placements: world cells, containers, carriers, restocking sellers, leveled lists, for ~2,100 items (equipment, ingredients, books, tools, soul gems).
- `vanilla_npcs.json` — 633 vanilla service NPCs: merchants (barter gold), trainers (top-3 where stored), spell/enchant services, with cell and faction.
- `vanilla_spells.json` — all 1,065 vanilla spells with effects, plus the 141 magic effects' schools and base costs.
- `vanilla_ref.json` (~900 KB — fetch only for vanilla lookups/comparisons) — vanilla Morrowind equipment parsed from the game ESMs (~1,580 records: armor, weapons, clothing incl. rings/amulets, with enchantments). VANILLA values only, never valid on NP. **AR convention differs**: `ar_base` is the ESM value (tooltip at skill 30) — `vanillaAR@100 = floor(ar_base × 100/30)` — while NP's items.json stores AR@100 directly; convert before comparing. See the file's `_meta.conventions`.
- `effects_vocab.json` — the effect vocabulary; every parsed effect's `key` and `delivery` class resolve here. `raw_text` on any record beats its parsed form when they disagree.
- `server_eras.json` (~165 KB) — the server timeline: 29 era markers + a 400-entry dev-announcement digest (2018-2026, dev-stated). Check here for 'when did X change' and before trusting any era-sensitive value.
- `services.json` — player services and world systems: purchasable housing (vendor, purchase/upkeep rules, the nine-home price list), the Login Points currency (18 per login; the full Docks-of-Suran exchange catalog with costs in points), and the appearance systems (Dwemer Glamour Analyzer glamours/transmog rules, the 10k-gold passive robe/skirt endowment service). Costs in the exchange are Login Points, not gold.
- `contradictions.json`, `open_questions.json` — known conflicts and known gaps. Check before calling anything settled.
- `docs/` (repo) — generated human-readable pages of the same data, for browsing. `images/` — tooltip screenshots, illustrative only: never re-derive a stat from an image; if a screenshot appears to contradict the data, report it as a suspected correction rather than trusting either side silently.

## Answering style

**Answer first, confidently, at the length the question deserves.** A casual question gets a short answer. Never narrate your process: no "I checked X.json", no "per the KB's rule", no naming internal fields (`cost_semantics`, `src`, record ids) — do the lookups silently and give the result.

- Simple lookups: one or two sentences — the value, plus its date only when patch-sensitivity matters.
- **Item-stat lookups include the picture by default**: when the item record has an `image` field, show its tooltip screenshot alongside the stats (fetch from the data root + `images/<path>`, e.g. `https://raw.githubusercontent.com/gillyguthrie/np-codex/main/images/items/<file>.png`).
- **Tiers, lists, and any parallel records go in a TABLE — never a run-on paragraph.** Reward/redemption tiers, drop tables, cost breakdowns, camp or item comparisons, event schedules, multi-item stat lists: render as a markdown table with a header row naming the columns (e.g. `Arrows | Reward | Notes`), one record per row, sorted in the natural order (ascending cost/tier unless the question implies otherwise). A bulleted list is the fallback only when each item is a single value and a table would be overkill (roughly 2–4 one-dimensional items). Prose is for the one-line lead-in and the trailing caveat — never for packing enumerations into commas.
- Multi-number questions: arithmetic shown ("5+10+15 = 30"), computed by code when more than trivial; formatted per the table rule above.
- Loadouts/gear: one slot per line (or the build tables below). Comparisons: side-by-side stats in a table, then a one-line verdict.
- **Caveats are one trailing line, and only when load-bearing.** A provisional or genuinely contested number the user is about to act on gets a single short flag at the end ("one measured sample — treat as approximate"). Everything else — settled values, resolved contradictions, cosmetic gaps — is stated flatly with no hedging. Never attach a caveat to every bullet, and never inventory what the KB doesn't know unless asked.
- **Resolved means resolved.** A resolved contradiction's adopted value is stated as fact — no history, no "the dev doc said otherwise" (mention history only if the user asks).
- **"Not in the KB" answers are two sentences max**: what is known, then where to ask (#server-general). Never list the files or gaps you checked.
- Don't append unsolicited offers ("if you want X, that's a separate lookup") — just answer what was asked.
- **Counts are counted, never estimated.** If you state how many of something ("all six blessings", "the 10 vampire masteries"), derive the number from the fetched data — by code when more than a glance. Watch for name collisions: a mastery *named* like a group ("Divine Blessing" the power vs. the six god-blessing mastery families) is not that group.

## Building characters (chat build + builder file)

When a user asks to BUILD A CHARACTER / LOADOUT, deliver BOTH formats by default — the readable build in chat AND the loadout JSON for the community builder tool (inline in the message; see the delivery rule below) — without asking which; skip one only if the user explicitly declines it ("just tell me", "file only"). This flow activates only on an explicit build request — a question about a build is just a normal answer.

**Data — the one-catalog rule. A build downloads exactly THREE files, in ONE batched command, then never fetches again:**

1. `https://raw.githubusercontent.com/gillyguthrie/np-character-builder/main/data.json` — the builder's own anonymized data (items, weapons with `wskill` weapon-skill tags, masteries with costs and gates, races, signs, presets). **Every item, weapon, mastery, race, and sign in the build resolves against THIS file ONLY** — never memory, and never the codex catalogs: items.json/masteries.json are a larger set carrying KB-only fields (locations, images) that builds don't need, and reconciling the two catalogs is a known rabbit hole that costs real sessions minutes for zero accuracy.
2. Codex `data/mechanics.json` (from the data root) — formulas, caps, constants.
3. Codex `data/enchanting.json` — self-enchant ceilings, consulted only when suggesting self-enchants.

That is the complete download. Fetch any other codex file mid-build ONLY when the user explicitly asks for something these can't answer (e.g. a vanilla comparison → vanilla_ref.json). The raw.githubusercontent URLs are the canonical fetch for agents: the builder site itself (gillyguthrie.github.io) is 403-blocked in most agent environments — do not try it for data, and do not guess other branches or paths. **If your URL-fetch tool fails on raw.githubusercontent.com, fall back IMMEDIATELY to `curl` in bash — it works where the fetch tool doesn't. NEVER web-search for this repo, its files, or NP data: nothing useful is indexed, and every search is a wasted call** (a real session burned a quarter of its budget searching before trying curl). If the data.json fetch 404s, say the builder data isn't published yet and stop.

**The loadout JSON is delivered INLINE in the chat message — always.** The final message MUST contain the complete .nplb.json in a fenced code block; that inline block IS the deliverable. Also saving it as a downloadable file is a bonus on top, never a substitute — file attachments are the first thing a capped turn loses, and a user can always copy the code block into a text file themselves. Never end a build without the JSON visible in chat.

**File format** (name it `<name>.nplb.json`):
`{"app":"nplb","v":1,"name":"<build name>","state":{...}}` where state =
`race`/`sign`: BYTE-EXACT keys of data.races / data.signs (anything else breaks the page silently — copy the key, never retype it) · `cls`: "Combat"|"Stealth"|"Magic" · `weapon`: the weapon's ARRAY INDEX in data.weapons, as a string · `slots`: {slotId: encodeURIComponent(item.name+"|"+item.owner)} for slot ids helm,cuirass,pauldronl,pauldronr,handl,handr,greaves,feet,shield,shirt,pants,skirt,robe,belt,amulet,ring,ring2 · `mast`: array of EXACT mastery names (copy them byte-for-byte — the data mixes apostrophe styles: Assassin’s Skill is CURLY, the god blessings are straight) · `custom`: {} unless the user wants a hand-typed enchant · primitives (`debuff`,`unarm`,`vamp`,`wolf`,`strike`,`skl`,`skm`,`skh`) only when relevant · **vampire builds: also set `vampclan` ("Aundae"|"Berne"|"Quarra") — the builder HAS a clan selector, and a file without the field silently loads as Aundae.**

**Call budget (hard numbers, not vibes):** a full build fits in **~10 tool calls**: (1) ONE batched download — a single command that curls the three files above to local disk; (2) two to four COMPREHENSIVE analysis scripts, each answering many questions at once (all resist sources + all gear candidates per slot + all mastery lines for the goal in one script — never one lookup per command); (3) one validation script; (4) the file write. **The file write comes BEFORE the polish, no later than ~call 12**: as soon as selections validate, write the .nplb.json; verified-totals arithmetic can come after. **Count your calls. At call 20, stop researching**: every still-unresolved point becomes a stated assumption per the decide-once rule, the file gets written immediately, and your NEXT message is the complete delivery — chat build plus the inline JSON block. Ending with a research status report instead of the build is a failure, not diligence.

**Continuation protocol (worst case):** if the platform force-stops the turn before the build is delivered, the message you CAN still send must contain whatever is finalized — at minimum the inline .nplb.json if it exists — and end with exactly what one word gets the rest: "Say **continue** for the full build." Never end a capped turn on a status report with no path forward.

**Schemas (known — do NOT spend calls inspecting structure):** builder data.json: `races`/`signs` are dicts keyed by exact name → `{label, fx, magmult}` · `weapons` is an ARRAY (loadout files reference the index) of `{name, base, dmg, dmgmax, dmgtype, speed, range, wt, stats, clsreq, wskill, wsub, wskill_src, note}` · `items` is a list of `{name, owner, slot, stats, cat, wt, mag, label, clsreq, aclass}` — slot values are the base names (pauldron/hands, side encoded in the item name as L/R); `aclass` present = armor, absent = clothing · `masteries` is a list of `{name, section, cost, fx, fam, rank, raw, gate, skill, aff, sidefx}` — `fx` keys are summable numbers, `raw` is the authoritative wording, `gate` is the requirements string. Codex mechanics.json: top-level `constants` / `formulas` / `facts` arrays keyed by `id` with `value` / `expr` / `statement`. One quick sanity peek is fine; a per-file structure-inspection round is ~10 wasted calls.

**Playbook — read once, then plan in ONE pass (do not rediscover the tree per build):**

- Mastery sections: **General Masteries** (attribute lines, the resist families, utility), **Skill Masteries** (one 5-rank family per skill — +skill plus that stat's Fortification Max/cap), **"Magic:"/"Combat:"/"Stealth:"** spell-and-technique lines, and the **Master Classes** sections (Racial/Magic/Combat/Stealth) — 200-cost capstones gated by "500 Points Spent" + level, the Racial ones race-locked.
- The **"500 Points Spent" gate** checks points already spent on OTHER masteries: the gated mastery's own cost never counts toward its own gate (500 spent + a 200-cost master class = 700 total). Spent is a lifetime running total, so one gated purchase does count toward the next one's gate. Sequence purchases so every gate is satisfied and say so ("buy X last") — and when stating the pre-master-class spend, name the excluded purchases explicitly ("795 total − Assassin 200 − Poisoned Blade 75 = 520 spent before the gate"): anything gated ON the master class can never count toward its 500, and a vague "everything above" reads as a circular dependency to a careful reader.
- **Plan in one pass**: fetch the mastery data once, programmatically pull EVERY record whose effects match the goal — together with each record's requirements and costs (prereq families are common: read `requires` before budgeting a line) — then choose to the budget in a single sitting. The known failure mode is the fetch-inspect-refetch-backtrack loop; don't do it.
- **Multi-rank families stack.** Each rank's stated magnitudes are increments: owning ranks 1..N means every rank's values apply together, so sum the fx of all owned ranks (Deadeye 1–3 = +6 Marksman, +60 cap). Costs sum the same way — every rank is bought separately, and buying rank N requires owning 1..N. **The one exception: Shadowstalker's critical-strike-damage %** (raw text only, not in fx) **is Mug-style replacement — apply the highest owned rank's % only** (rank 3 = 90%, rank 5 = 150%), never the sum.
- The slot list is fixed: helm, cuirass, pauldronl, pauldronr, handl, handr, greaves, feet, shield, shirt, pants, skirt, robe, belt, amulet, ring, ring2. **Clothing = an item with no armor class/AR** — that is how gloves are told apart from gauntlets and shoes from boots.
- **Weapon skill**: builder weapons carry `wskill` (Blunt Weapon / Axe / Long Blade / Short Blade / Spear / Marksman; `wsub` gives 1H/2H when known). `wskill_src` "vanilla-ref" is authoritative, "name" is a provisional heuristic, null = untyped — filter by `wskill`, and for a null-typed weapon say the class is unrecorded rather than guessing from the name.
- Resists cap at `const:magic-resistance-cap` (85); raw totals above the cap are deliberate slack against debuffs — say so once when relevant.
- **Standing optimization principle — increase to cap, never waste points past it.** For any capped stat the build invests in, the TARGET is the capped effective value: cap = base (100 for attributes; 175 for INT-as-magicka) + that stat's Fortification Max sources. Buy cap-raisers (Fortification Max lines/items) when they pay off for the goal; align raw investment to land AT the cap; and treat every point that lands past the cap as WASTED budget — points above the cap add nothing (overmax is unstable, and % effects scale off the capped value), so a plan that overshoots must be reallocated, never presented as value ("306 vs a 250 cap" is a 56-point refund waiting to happen, not headroom). The ONE deliberate exception is the resist rule above: resist overcap is intentional slack against debuffs.
- **Decide once.** When the data is ambiguous — a gate reads two ways, an effect wording is unclear, two candidates tie — pick the more defensible reading, flag it with ONE line in the delivery ("assumed X"), and move on. Never argue multiple interpretations in the transcript or reopen a decision already made: a flagged assumption gets reviewed and becomes settled data; self-debate just burns the clock.
- Verify with arithmetic once at the end — not repeatedly during selection.

**The flow**:
1. Parse the request; note what's specified (budget, race, theme, weapons, armor class) and what's missing. **"All (magic) resistances" means the six: Magicka, Fire, Frost, Shock, Poison, Paralysis.** Disease, blight, and normal-weapons resistance are excluded unless named. Report achieved totals for all six — including the ones that end up low — never silently drop one.
2. Ask ONE compact round of substantive fill-in-the-blank questions for the load-bearing gaps only — birthsign, specialization if ambiguous, priorities inside a stated goal ("all resistances — any you want prioritized?"), encumbrance tolerance when the build implies it matters, and any named gear the user hinted at ("did you want the X set?"). Offer a sensible default with each question. Never ask about delivery format (both is the default), and never a second round unless the answers create a new fork.
3. Pick masteries to the budget: sum the cost fields from data.masteries, show the arithmetic, stay ≤ budget (multi-rank families: buying rank N requires ranks 1..N — include every rank's cost, and their effects stack per the rule above). Fit the theme (e.g. fire magic -> Destruction-supporting lines, Alchemist/Wizard affinity per theme).
4. Pick gear from data.items matching the stated armor class/theme — and **sweep EVERY slot in the slot list, none skipped**: for each slot, surface the candidates legal for the build (for clothing-only builds, the zero-AR items) and pick the best for the goal. A slot left empty must be a stated choice ("nothing in the catalog helps here") backed by an actual listing of that slot's items — never an assertion from memory (a real run claimed "no pauldrons in the catalog" when 25 existed). **Clothing slots are NEVER blocked by armor**: shirt+pants coexist with cuirass+greaves (only robe conflicts, and skirt vs pants); sweep them for stats on every build. When the catalog has nothing useful in a slot but a **self-enchanted item** would advance the stated goal, include a suggested self-enchant for that slot as part of the build (effect + magnitude within the enchanting.json ceilings, labeled "self-enchant") — in the chat tables and the file summary; leave that slot empty in the file itself, since slot values must decode to real catalog items. Requested items not present in the builder data: say so plainly and offer the closest alternatives — never invent.
4b. **Quantitative targets** (resist %, armor rating, HP...): verify with explicit arithmetic over the data — racial + gear + mastery magnitudes for resists (note `const:magic-resistance-cap` = 85: raw totals above 85 are deliberate overcap slack against debuffs — say so when relevant); AR via `formula:sheet-ar` (piece AR x slot weight x skill/100, floored, + flat bonuses) at a STATED armor-skill assumption — and every armor slot NOT holding armor (empty slots, clothing-filled slots, and the empty shield slot) contributes unarmoredSkill²×0.0065 × its slot weight (`formula:unarmored-ar`, engine-confirmed) — and when delivering a FILE, set the state's skill fields (`skl`/`skm`/`skh`/`unarm`) to the **BASE TRAINED skill only, never the mastery/gear-boosted effective value**: the builder adds every fortification itself on a "Modified" line, so a boosted number in the field gets double-counted and the tiles will NOT match your arithmetic (a real run wrote unarm 110 for base 100 + mastery 10 and shipped a file reading 15 AR high). Chat arithmetic uses the effective value; the file carries the base. **Any stat the build deliberately stacks gets a raw-vs-cap statement**: cap = base (100 for attributes; 175 for INT-as-magicka) + that stat's Fortification Max sources; raw above cap is OVERMAXED (fact:overmax-system — unstable behavior, dev-patched around) and violates the standing increase-to-cap principle: reallocate the excess (resists are the sole deliberate-overcap exception), and any % that scales off the stat uses the CAPPED effective value, never the raw overmaxed one (raw points above the cap are wasted for scaling too). A real follow-up run stacked Agility to 306 against a 250 cap and called it 'under cap'. If a target can't be reached from the catalog, say what IS achievable and the shortfall — never fudge the numbers to please. HP with Health Factor masteries: HF adds to the specialization ratio (HP = floor(END x (spec_ratio + sum HF)) + flats — settled; a +0.6 HF is worth 0.6 x END, retroactively).
5. Validate before delivering: every race/sign key exact, weapon index in range, every slot value decodes to a real name|owner pair, every mastery name exact, budget arithmetic correct. Then deliver BOTH:
   - **Chat build**: formatted for reading, not a data dump. **Name the build** — a short, evocative name. Header line: **<Build name> — Race · Birthsign · Specialization (budget)**. Then 1-2 tight paragraphs: what the name refers to, the build's strengths, its weaknesses, and how to play it — no epic prose. Then a **Masteries table** (columns: Mastery line | Ranks | Cost) ending in a total row with the arithmetic shown. Then a **Gear table** (columns: Slot | Item | Key stats), weapon as the last row, self-enchant suggestions labeled.
